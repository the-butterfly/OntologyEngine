# OntologyEngine 愿景

> **status**: accepted | **phase**: mvp+phase1 | **source_of_truth**: 本文档 | **last_verified**: 2026-04-17

## 一句话定义

面向 AI Agent 的结构化知识推理引擎 —— 从**三类知识资产的融合视角**构建推理能力，支撑完整的业务场景，并实现"作业过程即知识沉淀"的闭环。

## 核心命题

传统知识库回答"是什么"，OntologyEngine 回答"意味着什么" —— 并将"意味着什么"转化为可执行的计算逻辑。

```
传统: 公司A注册资本1000万 → 存储
OntologyEngine: 公司A注册资本1000万 + 行业均值500万 → 资本充足度评级"高" → 触发授信规则 → 输出可追溯决策
```

## 三类知识资产：来源、特性与角色

### 资产分层总览

```
┌────────────────────────────────────────────────────────────────┐
│  L4: 组织级资产 (Organizational Assets)                     │
│  ── 业务规则、合规策略、行业标准、组织决策知识              │
│  ── 特征：共识性、权威性、版本化管理                            │
│  ── 来源：规章制度、操作手册、风险评分模型、决策表                │
│  ── 角色：业务规则引擎、标准化指标、可复用决策逻辑                │
├────────────────────────────────────────────────────────────────┤
│  L3: 个人知识沉淀 (Personal Knowledge)                        │
│  ── 专家经验、隐性知识、领域直觉、审查判断                    │
│  ── 特征：主观性、经验性、难以显性化                             │
│  ── 来源：Agent 交互、操作记录、用户反馈、个人归类规则               │
│  ── 角色：个人归类规则、分析逻辑、交互记忆                         │
├────────────────────────────────────────────────────────────────┤
│  L2: IT 资产 (IT Assets)                                         │
│  ── 数据源、API 接口、系统配置、基础设施元数据              │
│  ── 特征：结构化、可自动化、实时变化                                │
│  ── 来源：数据表、数据仓库、日志系统、API 端点                │
│  ── 角色：实例数据源、Schema 定义、推理基础                         │
└────────────────────────────────────────────────────────────────┘
         ↑ OntologyEngine 在三层之间建立可推理的链接 ↑
```

### 深度：三类资产的来源与特性差异

| 资产类型 | **来源**（具体从哪里来） | **特性**（有何独特之处） | **效力**（在决策中的权重） | **在 OntologyEngine 中的角色** |
|----------|--------------------------|----------------------------|------------------------------|------------------------------|
| **IT 资产**<br/>（L2 实例层） | • 数据库表（如 MySQL、PostgreSQL）<br/>• 数据仓库（如 Hive、ClickHouse）<br/>• 日志系统（如 ELK、Splunk）<br/>• API 端点（如 REST、GraphQL）<br/>• 消息队列（如 Kafka、RabbitMQ） | • **客观存在性**：数据事实，不受个人观点影响<br/>• **时效性强**：频繁更新，需实时同步<br/>• **结构化程度高**：Schema 约束明确（表结构、字段定义）<br/>• **权威性**：作为"单一事实源"（Single Source of Truth） | **组织级权威**，不受个人主观影响，作为推理的"客观基础" | • **Schema 定义**：通过 KGML 声明实体类型、属性、关系<br/>• **实例数据**：通过 IngestionService 导入 DuckDB<br/>• **推理基础**：L3/L4 分析的输入要素 |
| **个人资产**<br/>（L3 归类分析层） | • Agent 交互中的经验积累<br/>• 用户操作记录（如频繁使用的规则）<br/>• 个人偏好（如关注某些税种、特定风险阈值）<br/>• 用户反馈（如对结果的调整、修正）<br/>• 个人归类规则（如自定义的客户分类标准） | • **主观性强**：包含个人偏好、经验、习惯<br/>• **动态演进**：频繁变动，随时间成长<br/>• **隐私性**：属于个人，不应公开共享<br/>• **情境依赖性**：与特定任务、场景强相关 | **个人级有效**，仅限本人使用，他人不可见 | • **个人归类规则**：L2 CategoryValueDomain 的维度适用性规则<br/>• **个人分析逻辑**：L3 Indicator 的计算公式、分析路径<br/>• **交互记忆**：用户在 Agent 对话中的偏好、反馈 |
| **组织级资产**<br/>（L4 业务逻辑层） | • 企业规章制度（如风险管理指引）<br/>• 操作手册（如审批流程说明）<br/>• 风险评分模型（如 FICO、内部评分卡）<br/>• 决策表（如授信审批矩阵）<br/>• 业务规则库（如税务合规规则） | • **稳定性高**：经过审核和验证，变化频率较低<br/>• **权威性**：代表组织标准，需严格遵循<br/>• **可复用性**：跨部门、跨场景共享<br/>• **可追溯性**：版本管理、审计追踪 | **组织级权威**，需审核发布，所有用户遵循 | • **业务规则引擎**：L4 RuleEngine 的规则定义<br/>• **评分卡模型**：标准化风险评分体系<br/>• **决策表**：复杂决策逻辑的可视化 |

### 关键洞察

1. **IT 资产是"客观基础"**：所有推理的输入数据都来自这里，不受主观影响，保证决策的客观性
2. **个人资产是"个性化增强"**：每个人有不同的经验、偏好、习惯，需要适配，但要保护隐私
3. **组织资产是"标准化约束"**：代表组织共识，必须严格遵循，但可能需要个人经验的补充

## 资产融合、隔离与转换机制

### 融合：统一知识表示与推理

三类资产通过 **KGML Schema** 统一描述，在推理时按需融合：

```yaml
# Schema 声明中同时引用三类资产
entities:
  - name: LoanApplication
    # L2 IT 资产：数据源定义
    source:
      type: database_table
      table: loan_applications
      sync_interval: 5m  # 实时同步
    properties:
      - name: loan_amount
        source: column.amount
        type: decimal
    # L3 个人资产：用户自定义的归类规则
    personal_categories:
      - name: high_risk_customer
        owner: user_123
        rule: "annual_income < 50000 AND debt_ratio > 0.7"
        confidence: 0.85
        last_used: 2026-04-17
        usage_count: 42  # 累计使用次数，判断是否可沉淀
    # L4 组织资产：组织级的业务规则
    organization_rules:
      - name: credit_limit_formula
        version: v2.1
        status: active
        approved_by: risk_committee
        formula: |
          IF (credit_score >= 700 AND annual_income >= 100000)
          THEN min(annual_income * 0.5, 500000)
          ELSE min(annual_income * 0.3, 300000)
```

**融合的推理流程**：

```
┌────────────────────────────────────────────────────────────────┐
│ 步骤 1：输入要素收集（融合三类资产）                            │
├────────────────────────────────────────────────────────────────┤
│ • 从 IT 资产获取数据实例（LoanApplication 表记录）              │
│ • 从个人资产获取用户偏好（user_123 的归类规则）                    │
│ • 从组织资产获取规则约束（v2.1 授信规则）                      │
└────────────────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────────────────┐
│ 步骤 2：L2 归类（应用归类规则）                               │
├────────────────────────────────────────────────────────────────┤
│ • 应用个人归类规则（如有）：user_123 的高风险客户规则             │
│ • 应用组织归类规则：行业分类、企业规模分类等                       │
│ • 归类结果存储到实例的 category 字段                              │
└────────────────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────────────────┐
│ 步骤 3：L3 分析（计算指标，融合分析逻辑）                          │
├────────────────────────────────────────────────────────────────┤
│ • 计算组织标准指标：credit_score（信用分）、debt_ratio（负债率）  │
│ • 融合个人分析逻辑（如有）：user_123 的自定义指标计算公式         │
│ • 输出指标结果：credit_score=760, debt_ratio=0.4             │
└────────────────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────────────────┐
│ 步骤 4：L4 决策（执行业务规则，生成最终决策）                      │
├────────────────────────────────────────────────────────────────┤
│ • 执行组织授信规则：v2.1 授信公式                             │
│ • 生成决策结果：授信额度 = 500,000 元                           │
│ • 触发风险规则：如超过阈值，生成预警                            │
│ • 记录推理路径（ExecutionStepSnapshot）：可追溯、可解释                │
└────────────────────────────────────────────────────────────────┘
```

### 隔离：保护边界与权限

| 隔离维度 | IT 资产 | 个人资产 | 组织资产 |
|----------|-----------|----------|----------|
| **访问权限** | 按角色控制数据访问（如普通员工不能看薪资表） | 仅限本人访问（user_123 只能看到自己的个人资产） | 按角色控制规则访问（如规则管理员可编辑，普通用户只读） |
| **修改权限** | 需数据管理员审批（如修改表结构需 DBA 审核） | 本人可自由修改（用户可随时调整自己的归类规则） | 需规则管理员审批（如修改授信规则需风险委员会批准） |
| **可见性** | 部分数据敏感（如 PII 个人隐私信息，需脱敏） | 完全隐私（个人资产不对他人可见） | 组织内公开（非敏感规则，所有人可见） |
| **审计追踪** | 所有查询/修改记录（如数据访问日志） | 记录修改历史（如用户调整归类规则的时间、版本） | 版本管理、审批记录（如规则 v2.1 的审批人、变更理由） |
| **删除策略** | 数据保留策略（如日志保留 90 天） | 用户可随时删除（如清除个人归类规则） | 不删除（保留历史版本，支持回滚） |

### 转换：从经验到规范的演进

个人资产可以"晋升"为组织资产，形成知识沉淀闭环：

```
个人经验（动态）
    ↓ 累积验证（使用次数 + 置信度提升）
候选沉淀（标记 candidate_for_organization: true）
    ↓ 专家评审（规则管理员审核）
组织资产（规范）
    ↓ 广泛应用（所有用户使用）
通用知识（共享）
    ↓ 持续优化（收集反馈，迭代）
```

**转换机制的详细流程**：

| 阶段 | 活动 | 产出 | 判断标准 | 转换条件 |
|------|------|------|----------|----------|
| **个人积累** | 用户在 Agent 交互中反复使用某条归类规则或分析逻辑 | 个人归类规则（confidence=0.6） | 累计使用次数 ≥ 10 | 无（自然积累） |
| **标记候选** | 系统检测到频繁使用且置信度提升的规则，自动标记 | 候选组织资产（candidate_for_organization: true） | confidence ≥ 0.8 且 usage_count ≥ 20 | 自动标记 |
| **专家评审** | 规则管理员审核候选规则，验证有效性、安全性 | 审核意见（通过/拒绝/修改） | 规则逻辑正确、无安全风险、符合组织标准 | 人工审核 |
| **正式发布** | 审核通过后，进入组织规则库，版本管理 | 组织资产 v2.2（正式发布） | 审核通过 | 发布操作 |
| **持续优化** | 组织资产使用中收集反馈，迭代优化 | 组织资产 v2.3（优化版） | 收集到有效反馈 | 定期复盘 |

**转换示例**：

```
个人资产（user_123 的归类规则）：
  - name: high_risk_customer
    rule: "annual_income < 50000 AND debt_ratio > 0.7"
    confidence: 0.85
    usage_count: 42
    candidate_for_organization: true  # 系统自动标记

专家评审：
  - 审核人: risk_admin_001
  - 审核时间: 2026-04-17
  - 审核意见: "规则逻辑正确，但建议将阈值从 0.7 调整为 0.6，以覆盖更多风险场景"
  - 结论: 通过（需调整）

组织资产（正式发布）：
  - name: high_risk_customer
    version: v2.2
    rule: "annual_income < 50000 AND debt_ratio > 0.6"  # 调整后的阈值
    approved_by: risk_admin_001
    approved_at: 2026-04-17
    usage_count: 0  # 重新计数，跟踪组织内使用情况
```

## 作业过程即知识沉淀

OntologyEngine 的核心创新：**Agent 交互本身就是知识生产过程**

### 知识生产三阶段

| 阶段 | 活动 | 产出 | 沉淀到 | 记录机制 |
|------|------|------|---------|----------|
| **作业前** | Agent 接收任务，检索相关知识 | 上下文配置、输入要素 | 个人交互记忆（SessionCache） | 检索日志、上下文快照 |
| **作业中** | Agent 执行推理，调用规则引擎 | 推理路径、中间结果 | ExecutionStepSnapshot（全链路追溯） | 每个推理步骤的输入/输出/规则 |
| **作业后** | Agent 输出结果，用户反馈 | 最终决策、调整建议 | 个人资产（新的归类规则/分析逻辑） | 用户反馈记录、置信度更新 |

### 知识沉淀闭环示例：税务风险识别 Agent

```
┌────────────────────────────────────────────────────────────────┐
│ 阶段 1：作业前（检索与准备）                                  │
├────────────────────────────────────────────────────────────────┤
│ 用户提问："这家企业的税务风险如何？"                              │
│ • 从组织资产检索税务风险规则（如增值税虚开风险、所得税差异风险）           │
│ • 从个人资产检索用户过往偏好（如 user_456 关注增值税风险）               │
│ • 从 IT 资产检索企业数据（如申报记录、缴税数据、发票数据）             │
│ • 沉淀到 SessionCache：上下文配置（关注增值税风险）                   │
└────────────────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────────────────┐
│ 阶段 2：作业中（执行与推理）                                  │
├────────────────────────────────────────────────────────────────┤
│ • L2 归类：根据个人归类规则，识别高风险企业                      │
│   - 应用个人规则："连续 3 个月进项大于销项，标记为进项异常"            │
│ • L3 分析：计算税务风险指标，融合个人分析逻辑                      │
│   - 计算指标：税负率、发票金额波动、供应商集中度                      │
│   - 融合个人逻辑："税负率 < 行业均值 * 0.8，提升风险等级"              │
│ • L4 决策：应用组织税务规则，生成风险意见                         │
│   - 执行规则："增值税虚开风险 = (进项发票金额 - 销项发票金额) / 总销售额 > 0.3"  │
│   - 生成风险意见：高风险，建议深入稽查                               │
│ • 全程记录推理路径（ExecutionStepSnapshot）：                           │
│   - 步骤 1：输入要素（企业数据、规则、偏好）                          │
│   - 步骤 2：L2 归类结果（进项异常）                              │
│   - 步骤 3：L3 分析结果（税负率 2.1%，行业均值 4.5%）               │
│   - 步骤 4：L4 决策结果（高风险）                                │
└────────────────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────────────────┐
│ 阶段 3：作业后（反馈与沉淀）                                  │
├────────────────────────────────────────────────────────────────┤
│ 用户反馈："风险判断准确，但我还想关注发票金额波动"                      │
│ • 个人归类规则/分析逻辑自动提升置信度（如从 0.6 → 0.7）                │
│ • 用户调整规则：新增"发票金额波动 > 50%，标记为异常"                 │
│ • 更新个人资产：user_456 的归类规则库                              │
│ • 记录用户反馈：在 SessionCache 中记录用户偏好变更                    │
│ • 标记候选组织资产（如累计使用次数 ≥ 20，自动标记）                    │
└────────────────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────────────────┐
│ 阶段 4：沉淀转化（从个人到组织）                                │
├────────────────────────────────────────────────────────────────┤
│ • 个人规则累积验证后，提交专家评审                               │
│ • 专家审核：验证规则有效性、安全性、合规性                          │
│ • 评审通过：转换为组织资产（v2.2 规则）                           │
│ • 所有用户共享新规则：知识增值                                  │
│ • 持续优化：收集反馈，迭代优化（如阈值调整、条件补充）                    │
└────────────────────────────────────────────────────────────────┘
```

## 典型场景支撑

### 场景 1：BI 系统问数 Agent

| 能力需求 | 资产来源 | OntologyEngine 贡献 | 三层融合机制 |
|----------|----------|-------------------|--------------|
| **数据表结构理解** | IT 资产（数据仓库的表结构、字段定义） | Schema 定义 + 实例数据导入 | IT 资产提供客观基础 |
| **指标计算逻辑** | 组织资产（指标定义库、行业标准） | L3 Indicator 引擎（公式计算、指标评分） | 组织资产提供标准化约束 |
| **个性化分析偏好** | 个人资产（用户分析习惯、常用指标） | 个人归类规则 + 分析路径 | 个人资产提供个性化增强 |
| **问答推理** | 三层融合 | L2→L3→L4 四层推理 | 融合三类资产生成准确答案 |

**推理流程**：
```
用户提问："今年Q1的销售额是多少？"
  ↓
IT 资产：从 sales_fact 表查询 Q1 数据（客观事实）
  ↓
个人资产：用户偏好使用 GMV（成交金额）指标，而非销售额
  ↓
组织资产：应用标准指标计算公式（GMV = 订单金额 - 退款金额）
  ↓
推理结果：Q1 GMV = 1,234,567 元
  ↓
沉淀：记录用户偏好（偏好 GMV 指标），提升未来问答效率
```

### 场景 2：企业知识问答 Agent

| 能力需求 | 资产来源 | OntologyEngine 贡献 | 三层融合机制 |
|----------|----------|-------------------|--------------|
| **发文/流程/规定检索** | 组织资产（规章制度库、操作手册） | L4 规则引擎 + 语义检索（向量 + 图遍历） | 组织资产提供权威来源 |
| **上下文关联** | IT 资产（业务系统数据、流程实例） | Schema 驱动的实体关联（如流程ID → 执行记录） | IT 资产提供上下文信息 |
| **个人场景适配** | 个人资产（用户工作场景、常用流程） | 个人归类规则 + 交互记忆 | 个人资产提供场景适配 |

**推理流程**：
```
用户提问："报销审批流程是什么？"
  ↓
组织资产：检索财务制度（报销管理办法 v3.2）
  ↓
IT 资产：关联流程实例（最近 10 条审批记录，平均耗时 2.3 天）
  ↓

  ↓
推理结果：报销审批流程（含电子签名选项） + 历史耗时参考
  ↓
沉淀：记录用户场景（偏好电子签名），优化未来推荐
```

| 能力需求 | 资产来源 | OntologyEngine 贡献 | 三层融合机制 |

  ↓

## 技术哲学

1. **Schema 即代码** —— 业务知识用声明式 YAML 定义，非硬编码
2. **本地优先** —— 单机可运行百万级节点，零外部依赖
3. **AI Native** —— 为 Agent 设计 Memory 接口，非事后兼容
4. **资产可链接** —— 三层知识资产通过统一本体模型实现可推理关联
5. **作业即沉淀** —— Agent 交互本身就是知识生产过程，个人资产可转换为组织资产

## 上下文栈定位

OntologyEngine 在 AI Agent 的上下文栈（Context Stack）中占据**深度层**：

```
┌─────────────────────────────────────────────────────┐
│  AI Memory (连续性层)                                │
│  ── 跨会话状态、用户偏好、学习到的事实                 │
│  ── 保障 Agent 行为连续性                             │
│  ── 类比 m-flow 的 Procedural Memory（程序记忆）            │
├─────────────────────────────────────────────────────┤
│  RAG (广度层)                                        │
│  ── 文档检索、知识密集型问答                          │
│  ── 保障信息覆盖广度                                  │
│  ── 类比传统 RAG 系统（向量检索）                         │
├─────────────────────────────────────────────────────┤
│  ★ Knowledge Graph / OntologyEngine (深度层) ★       │
│  ── 实体关系、多跳推理、结构化推断                     │
│  ── 保障推理深度和可解释性                             │
│  ── 三层资产链接的载体                                │
│  ── 类比 m-flow 的 Episodic Memory（情节记忆） + KAG 的 Logical Form │
└─────────────────────────────────────────────────────┘
```

### 对齐 m-flow 的设计

| m-flow 概念 | OntologyEngine 对应 | 融合点 |
|--------------|-------------------|----------|
| **Episode**（场景存储） | L1 事实层（实例数据） | 存储完整的业务场景（如贷款申请记录） |
| **Facet**（维度分类） | L2 归类层（分类规则） | 从多个维度对场景进行分类（如行业、规模、风险等级） |
| **FacetPoint**（原子断言） | L3 分析层（指标计算） | 从维度中提取具体的指标值（如信用分=720） |
| **Entity**（命名实体） | Schema 实体定义 | 跨场景的实体关联（如客户ID、产品代码） |
| **Cone Graph**（倒锥形图） | 四层推理（L1→L2→L3→L4） | 从精确的指标（尖端）推理到决策（底部） |

### 对齐 KAG 的设计

| KAG 概念 | OntologyEngine 对应 | 融合点 |
|-----------|-------------------|----------|
| **Logical Form Planner**（逻辑形式规划） | L2 归类层 + L3 分析层 | 将业务问题分解为可执行的逻辑形式（如归类、计算、决策） |
| **Executor**（执行器） | L4 规则引擎 | 执行逻辑形式，包括 op_deduce（演绎）和 op_retrieval（检索） |
| **OpenSPG 引擎** | Schema 驱动的图存储 | 统一的本体模型，支持结构化知识推理 |
| **互索引结构** | IT↔组织资产的双向关联 | 知识图谱与数据表的互索引，支持双向查询 |

> **关键洞察**：OntologyEngine 不仅对齐了 m-flow 的四层 cone graph 和 KAG 的逻辑形式引导推理，更在此基础上创新了**三类资产的融合、隔离、转换机制**，以及**作业过程即知识沉淀的闭环设计**，使得知识不只是"存储"，而是"持续生产的活资产"。

## 知识碎片与结构化知识的双轨管理

### 问题：知识的两种形态必须共存

企业知识天然以两种形态并存：
- **结构化知识**：实体关系图、业务规则、指标公式、分类标准 —— 精确、可推理、可执行
- **知识碎片**：制度文件、操作手册、审查意见、外部报告 —— 丰富、非结构化、来源多样

传统系统的做法是二选一：要么只做知识图谱（丢失碎片中的丰富上下文），要么只做文档检索（无法结构化推理）。OntologyEngine 的选择是**双轨共存 + 互索引**。

### 互索引：从知识碎片到结构化推理的桥梁

借鉴 KAG 的 AtomicQuery 桥接层和 m-flow 的 `supported_by` 边设计，OntologyEngine 建立了四种互索引关系：

| 互索引关系 | 方向 | 作用 | 场景 |
|------------|------|------|------|
| `extracted_from` | 实体 → 碎片 | "这个实体来自哪个文档的哪个段落" | 授信规则 R001 定义在《授信管理办法》第 3.2 节 |
| `supported_by` | 碎片 → 实体 | "这个文档段落支撑了哪个业务判断" | 专家审查笔记支撑了高风险归类 |
| `defined_in` | 规则/指标 → 碎片 | "这条规则/公式的定义来源" | 信用分公式定义在《风险评分模型 v2.1》 |
| `trace_to` | 推理步骤 → 碎片 | "这个决策可追溯到哪些原始材料" | 授信额度 500 万 → 企业财报 + 评分卡文档 + 审批记录 |

**与 KAG 的差异**：KAG 只做实体↔文本块的桥接，OntologyEngine 还做**规则↔碎片**和**推理链↔碎片**的溯源 —— 因为业务场景要求每个决策都能追溯到权威来源。

**与 m-flow 的差异**：m-flow 的 `supported_by` 是单向挂载（碎片挂到 Facet/Episode），OntologyEngine 实现**双向导航** —— 既可以从碎片出发找到关联的结构化知识，也可以从结构化知识溯源到来源碎片。

### 关系语义：边是推理的参与者，不是被动的连接器

借鉴 m-flow 的核心设计突破 —— **"边有语义"（Edges Have Semantics）**，OntologyEngine 中的每条关系不仅携带类型标签，还携带：
- **边文本（edge_text）**：自然语言描述，参与向量检索
- **语义权重（weight）**：数值化的关系重要性，参与路径评分和传递推理
- **边属性（attributes）**：业务属性（如担保金额、有效期、审批人）

这使得关系边从"被动的管道"变为"主动的语义过滤器"：

```
传统知识图谱：  A ──[guarantees]──▶ B    ← 边只是标签
m-flow：        A ──["A向B提供500万担保"]──▶ B  ← 边参与检索排序
OntologyEngine：A ──["A向B提供500万担保", weight=0.8, amount=500万, type=financial]──▶ B
                ↑ 边参与检索排序 + 传递推理 + 规则执行
```

### 语义推理：在图结构上做业务计算

m-flow 用成本传播（tip→base）做检索排序 —— **"一条强证据链足以证明相关性"**（Minimum, Not Average）。OntologyEngine 将这个思想扩展到业务推理：

| 推理类型 | 机制 | 场景 |
|----------|------|------|
| **确定推理** | DAG 规则执行（RuleEngine） | 信用分计算、风险等级判定、授信额度审批 |
| **传递推理** | 图遍历 × 语义权重衰减 | 担保链风险传导（A→B→C→D，风险逐跳衰减） |
| **语义推理** | 边文本向量距离参与排序 | "找与'担保链风险'最相关的知识路径" |

关键差异：
- m-flow 的路径成本 → 服务于**检索排序**（越低越好）
- OntologyEngine 的传递推理 → 服务于**业务计算**（如风险传导值 = 原始风险 × 0.8 × 0.6 × 0.3）

### 知识点全生命周期

借鉴 m-flow FacetPoint 的"独立可检索、独立评分、独立关联证据"设计，OntologyEngine 对图中每个原子知识单元进行全生命周期管理：

```
创建 → 关联 → 版本化 → 演进 → 溯源 → 归档
  │      │      │       │      │      │
  ↓      ↓      ↓       ↓      ↓      ↓
导入   互索引  快照    沉淀   Provenance  保留
定义   关系   diff    转化   Link       历史
交互   权重   审批    反馈   证据链     标记
```

**知识点质量标签**：每个知识点附带新鲜度、置信度、权威性、覆盖率、一致性五个质量维度，让 Agent 在作业时可以判断知识的可靠程度。
