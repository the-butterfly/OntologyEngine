# 项目目标

> **status**: accepted | **phase**: mvp+phase1 | **source_of_truth**: 本文档（阶段目标） | **last_verified**: 2026-04-17

## 阶段目标

### Phase 0: MVP (当前)
**Deadline**: 2026-04-30

| 目标 | 验收标准 | 三类资产视角 |
|------|----------|--------------|
| **Schema 可定义** | KGML YAML 解析通过 | 支持 IT 资产（数据源）、个人资产（归类规则）、组织资产（业务规则）的声明 |
| **规则可执行** | 供应链金融 5 条规则跑通 | 验证 L4 规则引擎可执行组织资产 |
| **Demo 可演示** | 单脚本运行完整流程 | 验证 L1-L4 四层推理链路 |

### Phase 1: 可用 (4周)
**Deadline**: 2026-05-31

| 目标 | 验收标准 | 三类资产视角 |
|------|----------|--------------|
| **查询高性能（分级目标）** | 简单查询 P99 < 200ms / 图遍历 P99 < 2s / 混合检索 P99 < 1s | 支持三类资产混合查询（IT 数据 + 个人规则 + 组织规则） |
| **规则热更新** | YAML 修改后秒级生效 | 组织资产可实时更新，个人资产即时生效 |
| **本地图分析** | Kuzu 嵌入图数据库接入，图遍历/路径查询/担保圈检测可用 | 支持 IT 资产（数据实例）的图遍历和路径分析 |
| **本地管理面基础** | Space + Schema CRUD + 消费视图 API，配置驱动部署模式切换 | 支持三类资产的 CRUD 操作 |
| **平台化基础** | 审计 Schema 纳入存储表，DuckDB 本地持久化 | 支持组织资产的版本管理和审计追踪 |
| **三层资产链接基础** | IT 资产（数据实例）↔ 组织资产（规则定义）双向链接可验证 | 验证 Schema 驱动的 IT↔组织链接 |
| **个人知识沉淀基础** | 专家经验可通过 YAML 声明式编码为可执行规则 | 验证个人资产可通过 YAML 声明 |
| **Dataset 注册与 Fragment 存储** | Dataset 元数据声明可配置，KnowledgeFragment 存储可用 | Layer-R 原文碎片存储，支持向量索引 |
| **互索引基础** | extracted_from / trace_to 双向链接可验证 | Layer-R ↔ Layer-S 互索引可运行 |

> **本地优先选型说明**：Phase 1 完全基于本地存储（DuckDB + Kuzu），不依赖任何外部服务。
> - DuckDB：实体存储、指标计算、审计日志、SQL 查询
> - Kuzu（本地图数据库）：图遍历、路径查询、担保圈检测、循环检测
> - 两者通过统一 Repository 接口协同

### Phase 2: 好用 (4周)
**Deadline**: 2026-06-30

| 目标 | 验收标准 | 三类资产视角 |
|------|----------|--------------|
| **AI Native 能力** | MCP 协议支持，Claude Agent 可调，含管理面和消费面工具 | 支持 Agent 交互中自动沉淀个人资产 |
| **可视化** | Schema/规则链/执行结果的 Web UI | 可视化三类资产的关联和推理路径 |
| **50W 节点支撑** | Kuzu 优化，内存图索引，向量检索集成 | 支持大规模 IT 资产（数据实例） |
| **多场景** | 3 个垂直领域 Schema | 覆盖典型场景（BI 问数、知识问答、风险识别、税务意见出具） |
| **上下文栈集成** | Memory + RAG + KG 三层联合查询能力，四阶段集成流程可用 | 与 Agent Memory（连续性层）和 RAG（广度层）协同 |
| **个人→组织沉淀闭环** | Agent 辅助知识提取 → 人工确认 → 组织规则库更新 | 验证个人资产可转换为组织资产的完整流程 |
| **资产链接可视化** | 三层资产之间的依赖和传播路径可视化 | 可视化 IT↔个人↔组织的链接关系 |
| **Layer-R/S 协同检索** | Layer-R 向量检索 → Layer-S 推理 → trace_to 回溯，完整链路可用 | 验证互索引驱动的协同推理流程 |
| **矛盾检测** | Ingestion 时矛盾检测触发，异步扫描可用 | 支持跨 Dataset 的数据一致性管理 |
| **时序查询** | 时序实体支持 as_of 查询，默认返回当前版本 | 支持历史数据回溯 |

### Phase 3: 规模化 (4周)
**Deadline**: 2026-07-31

| 目标 | 验收标准 | 三类资产视角 |
|------|----------|--------------|
| **反馈闭环** | 反馈自动触发影响分析 + 生成建议，人工确认执行 | 验证三类资产变更的影响分析和传播机制 |

## 技术指标

| 指标 | MVP | Phase 1 | Phase 2 | Phase 3 |
|------|-----|---------|---------|---------|
| **节点数** | 1K | 100K | 500K | 2M+ |
| **简单查询 P99** | 1s | 200ms | 100ms | 50ms |
| **图遍历 P99** | - | 2s | 1s | 500ms |
| **混合检索 P99** | - | 1s | 500ms | 300ms |
| **规则数** | 10 | 20 | 200 | 1000 |
| **部署依赖** | 0 | 0 | 0 | 可选外部存储 |
| **资产链接覆盖** | - | IT↔组织 | + 个人↔组织 | 三层完整 |
| **决策可追溯** | - | 规则级 | 规则 + 数据级 | 三层全链路 |

> **选型约束**：Phase 1-2 坚持零外部依赖，所有能力运行在单机本地。
> Phase 3 才引入可选的外部存储后端（DuckDB 保持为默认）。

## 三类资产管理的核心目标

### 目标 1：资产管理维度

| 管理维度 | 当前痛点 | OntologyEngine 目标 |
|----------|----------|---------------------|
| **规则定义** | 硬编码 if/else，分散在代码中 | YAML 声明式，Schema 即代码，统一管理三类资产 |
| **规则执行** | 手动编排顺序，难以保证正确性 | DAG 拓扑自动排序，支持 L1-L4 四层推理 |
| **规则变更** | 发版部署，周期长（周级） | 热更新，秒级生效，支持组织资产实时发布 |
| **规则追溯** | 无法解释决策，不知道用了哪条规则 | ExecutionStepSnapshot + ConditionExplainer，全链路追溯 + 中文解释 |
| **规则影响** | 改一处怕崩全局，无法分析影响范围 | 影响链分析 + 变更传播，自动识别受影响的规则和数据 |
| **规则沉淀** | 专家经验流失，无法传承 | 个人知识 → 组织资产的持续转化机制（使用次数 + 置信度） |
| **规则验证** | 上线后才发现问题，影响生产环境 | dry_run 模拟 + what-if 对比，上线前验证 |

### 目标 2：知识沉淀维度

| 沉淀维度 | 当前痛点 | OntologyEngine 目标 |
|----------|----------|---------------------|
| **个人经验结构化** | 经验只在脑子里，无法编码 | YAML 声明式，个人归类规则/分析逻辑可直接编码 |
| **个人→组织转换** | 经验无法传承，重复劳动 | 使用次数 + 置信度累积，自动标记候选资产，专家评审后转换 |
| **作业即生产** | Agent 交互只是消费，不生产知识 | 作业前/中/后全流程记录，交互本身就是知识生产 |
| **反馈驱动优化** | 规则更新依赖人工，周期长 | 用户反馈自动影响分析，生成优化建议，人工确认执行 |
| **知识治理** | 规则版本混乱，无生命周期管理 | 新鲜度评分 + 血缘追踪 + 语义标签 + 所有权元数据 |

### 目标 3：典型场景支撑维度

| 场景 | 支撑目标 | 验收标准 |
|------|----------|----------|
| **BI 系统问数 Agent** | • 数据表结构理解（IT 资产）<br/>• 指标计算逻辑（组织资产）<br/>• 个性化分析偏好（个人资产）<br/>• 问答推理（三层融合） | • Schema 定义数据表和指标<br/>• 支持个人归类规则<br/>• L1-L4 四层推理可用 |
| **企业知识问答 Agent** | • 发文/流程/规定检索（组织资产）<br/>• 上下文关联（IT 资产）<br/>• 个人场景适配（个人资产） | • L4 规则引擎支持语义检索<br/>• IT 资产与组织资产关联<br/>• 个人归类规则支持 |
| **个人作业辅助 Agent** | • 数据分析（IT 资产）<br/>• 文档结构化（个人资产）<br/>• 知识检索（组织资产）<br/>• 效率提升（个人→组织转换） | • 实例数据导入 + L3 计算指标<br/>• L2 归类引擎可用<br/>• 个人资产可转换为组织资产 |
| **业务场景分析 Agent**（风险识别/税务意见出具） | • 指标/要素定量分析（IT + 组织）<br/>• 定性分析 LLM 判定（组织 + IT）<br/>• 风险识别（组织 + 个人）<br/>• 税务意见出具（组织 + IT） | • L3 Indicator 引擎可用<br/>• L4 LLMJudge 算子可用<br/>• L2→L3→L4 推理可用 |

### 对齐 m-flow/KAG 的设计

| m-flow/KAG 概念 | OntologyEngine 对齐 | 阶段目标 |
|------------------|-------------------|----------|
| **m-flow 的 Cone Graph**（四层倒锥形图） | 对齐 L1-L4 四层推理架构 | Phase 0：MVP 验证四层推理链路 |
| **m-flow 的 Bundle Search**（图路由检索） | 对齐混合检索（图 + 向量 + 规则） | Phase 1：混合检索 P99 < 1s |
| **m-flow 的 Episodic Memory**（情节记忆） | 对齐 ExecutionStepSnapshot（全链路追溯） | Phase 1：决策可追溯至规则级 |
| **m-flow 的 Procedural Memory**（程序记忆） | 对齐个人资产（归类规则/分析逻辑） | Phase 2：个人→组织沉淀闭环 |
| **KAG 的 Logical Form**（逻辑形式规划） | 对齐 L1-L4 四层推理链（事实 → 归类 → 分析 → 决策） | Phase 1：四层推理链路可用 |
| **KAG 的 Executor**（逻辑执行） | 对齐 L4 规则引擎（规则执行 + op_deduce + op_retrieval） | Phase 1：规则热更新，秒级生效 |
| **KAG 的 OpenSPG 引擎**（Schema 约束） | 对齐 KGML Schema（统一知识描述语言） | Phase 0：KGML YAML 解析通过 |

## 非目标

明确不做，避免范围蔓延：

1. **通用 NLP 平台** —— 专注结构化知识推理，不做通用文本理解
2. **替代数据仓库** —— 不做 OLAP，专注实时规则推理
3. **可视化编排** —— Phase 2 前无拖拽式规则设计器
4. **多租户 SaaS** —— Phase 3 前不考虑租户隔离
5. **通用文档检索** —— RAG 广度层由外部系统提供，OntologyEngine 专注深度推理层
6. **Agent 会话记忆** —— Memory 连续性层由外部 Agent 框架提供，OntologyEngine 提供知识接口

## 成功标准的业务价值

### 价值 1：提升决策效率

| 指标 | 现状 | 目标 | 提升幅度 |
|------|------|------|----------|
| 规则修改周期 | 1 周 | 秒级 | 提升 60,000 倍 |
| 决策响应时间 | 1-5 分钟（人工审批） | < 500ms（自动推理） | 提升 100 倍 |
| 决策追溯时间 | 几天（人工复盘） | 实时（自动追溯） | 提升 100% |

### 价值 2：降低知识流失风险

| 指标 | 现状 | 目标 | 提升幅度 |
|------|------|------|----------|
| 专家经验结构化率 | 0%（完全依赖脑子） | 80%（可编码） | 新增能力 |
| 个人→组织转换率 | 0%（无法转换） | 60%（自动标记 + 评审） | 新增能力 |
| 知识复用率 | 20%（重复劳动） | 80%（共享复用） | 提升 300% |

### 价值 3：增强决策可解释性

| 指标 | 现状 | 目标 | 提升幅度 |
|------|------|------|----------|
| 决策可追溯率 | 0%（黑盒） | 100%（全链路） | 新增能力 |
| 决策解释覆盖 | 0%（无解释） | 100%（中文拆解） | 新增能力 |
| 决策影响分析 | 几天（人工排查） | 实时（自动分析） | 提升 100% |
