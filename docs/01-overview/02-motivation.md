# 为什么需要 OntologyEngine

> **status**: accepted | **phase**: mvp+phase1 | **source_of_truth**: 本文档 | **last_verified**: 2026-04-17

## 三层知识资产断裂：企业知识管理的核心矛盾

当前企业知识管理的核心矛盾不是"缺知识"，而是**三类知识资产之间断裂** ——

IT 资产（数据、系统、API）、个人资产（专家经验、操作习惯）、组织资产（规章制度、业务规则）各自为政，无法形成可追溯的完整决策链。

```
┌─────────────────────────────────────────────────────────────────────┐
│  L4: 组织级资产                                             │
│  ── 业务规则、合规策略、行业标准、组织决策知识                    │
│  ── 来源：规章制度、操作手册、风险评分模型、决策表                  │
│                          ↑ 断裂                              │
│  ── 表现：规则与数据脱节，决策过时，无法追溯推理过程                │
├─────────────────────────────────────────────────────────────────────┤
│  L3: 个人知识沉淀                                           │
│  ── 专家经验、隐性知识、领域直觉、审查判断                          │
│  ── 来源：Agent 交互、操作记录、用户反馈、个人归类规则                 │
│                          ↑ 断裂             断裂 ↓              │
│  ── 表现：经验只在脑子里，退休后规则成谜，无法传承                   │
├─────────────────────────────────────────────────────────────────────┤
│  L2: IT 资产                                               │
│  ── 数据源、API 接口、系统配置、基础设施元数据                      │
│  ── 来源：数据表、数据仓库、日志系统、API 端点                       │
│                          ↑ 断裂                              │
│  ── 表现：系统告警无人能解释，数据异常依赖人工经验                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 三类资产断裂的具体表现

| 断裂类型 | 表现（业务视角） | 后果 | 真实案例 |
|----------|------------------|------|----------|
| **IT ↔ 组织** | • 系统数据变了（如新增字段）但规则没更新<br/>• 规则变了（如调整授信阈值）但系统未同步 | • 规则与数据脱节，决策过时<br/>• 数据更新后规则失效，业务中断 | • 某银行新增"税务信用评分"字段，但授信规则未更新，导致新客户无法授信 |
| **个人 ↔ 组织** | • 专家经验只存在于脑子里，未结构化<br/>• 专家退休后，规则成谜，无法传承<br/>• 新员工无法快速学习经验 | • 组织能力退化，知识无法传承<br/>• 重复犯错，效率低下 | • 某税务专家退休后，其"进项异常判断"经验随人走，新员工无法复现 |
| **IT ↔ 个人** | • 系统告警无人能解释，依赖人工经验<br/>• 数据异常依赖专家判断，无法自动化<br/>• 个人无法快速理解系统数据 | • 响应慢、漏判多<br/>• 人工成本高，风险隐患 | • 某监控系统触发"担保链异动"告警，但无人能解释具体风险含义，延误处理 |
| **三层孤岛** | • IT 数据 / 专家经验 / 组织规则各自为政<br/>• 无法形成可追溯的完整决策链<br/>• 改一处怕崩全局，影响分析困难 | • 无法追溯决策来源<br/>• 合规风险，审计困难<br/>• 知识更新无影响分析 | • 某授信决策失败，无法追溯是数据错误、规则缺陷还是经验误判 |

## 痛点矩阵：从业务场景出发

| 痛点 | 根因（资产断裂） | 后果（业务影响） | 典型场景 |
|------|-----------------|----------------|----------|
| **规则散落在代码里** | 个人知识未沉淀为组织资产 | 改规则需发版，业务等不及 | 供应链金融、风险识别 |
| **数据与知识割裂** | IT 资产与组织资产断裂 | 模型用不全，决策拍脑袋 | BI 问数、税务意见出具 |
| **AI 不懂业务** | 个人知识未结构化为可推理资产 | 幻觉多，不敢用于核心决策 | 业务场景分析、知识问答 |
| **专家经验流失** | 个人→组织资产沉淀链断裂 | 组织能力退化，重复犯错 | 所有场景（普遍痛点） |
| **决策无法追溯** | 三层资产未链接，无法回溯 | 审计困难，合规风险 | 风险识别、税务意见出具 |
| **知识更新无影响分析** | 组织资产变更无传播机制 | 牵一发动全身，改一处怕崩全局 | 所有场景（普遍痛点） |

## 典型场景的痛点分析

### 场景 1：BI 系统问数 Agent

| 问题 | 根因（资产断裂） | 后果 |
|------|-----------------|------|
| **数据表结构理解困难** | IT 资产（数据仓库）与组织资产（指标定义）断裂 | Agent 无法理解"销售额"与"GMV"的区别，回答错误 |
| **指标计算逻辑不一致** | 组织资产（指标定义库）与 IT 资产（数据表）断裂 | 不同团队用不同公式计算"毛利率"，数据口径不一致 |
| **个性化分析偏好无法应用** | 个人资产（用户分析习惯）与组织资产（标准指标）断裂 | 用户习惯使用"净利率"而非"毛利率"，但 Agent 无法适配 |
| **问答推理无法解释** | 三层资产未链接，无法追溯推理过程 | 用户无法理解"为什么是这个答案"，信任度低 |

**传统方案的盲区**：
- 纯 RAG：检索文档片段，无推理，无法计算指标
- 传统 SQL：硬编码查询，无法适配个性化偏好
- 数据仓库：只能存储数据，无法承载规则和经验

### 场景 2：企业知识问答 Agent

| 问题 | 根因（资产断裂） | 后果 |
|------|-----------------|------|
| **发文/流程/规定检索不准确** | 组织资产（规章制度库）与 IT 资产（业务系统数据）断裂 | 无法关联流程与实际执行记录，检索结果泛化 |
| **上下文关联困难** | IT 资产（数据表）与组织资产（知识库）断裂 | 用户问"报销流程"，无法关联最近审批耗时、常见错误 |
| **个人场景无法适配** | 个人资产（用户工作场景）与组织资产（知识库）断裂 | 不同用户问同样问题，回答相同，无法适配个人偏好 |
| **新规定无法热更新** | 组织资产（规则）与 IT 资产（系统）断裂 | 新政策发布后，系统无法自动更新，需手动同步 |

**传统方案的盲区**：
- 纯向量检索：语义相似但不准确，无上下文关联
- 传统搜索：关键词匹配，无法理解自然语言
- 文档管理：只能存储，无法推理和关联

### 场景 3：个人作业辅助 Agent

| 问题 | 根因（资产断裂） | 后果 |
|------|-----------------|------|
| **数据分析效率低** | IT 资产（数据表）与个人资产（归类规则）断裂 | 用户每次都手动筛选数据，无法复用经验 |
| **文档结构化依赖人工** | 个人资产（归类逻辑）未结构化 | 每次都手动分类，效率低下，易出错 |
| **知识检索不精准** | 组织资产（知识库）与 IT 资产（数据）断裂 | 检索结果与实际数据脱节，无法关联上下文 |
| **经验无法沉淀** | 个人资产无法转换为组织资产 | 重复劳动，团队知识无法共享 |

**传统方案的盲区**：
- 纯工具：只能辅助操作，无法沉淀经验
- 手动流程：依赖人工，无法自动化
- 文件存储：无结构化，无法推理

### 场景 4：业务场景分析 Agent（风险识别/税务意见出具）

| 问题 | 根因（资产断裂） | 后果 |
|------|-----------------|------|
| **指标/要素定量分析不准确** | IT 资产（业务数据）与组织资产（指标定义）断裂 | 指标计算公式不一致，数据口径混乱 |
| **定性分析（LLM 判定）无依据** | 组织资产（业务规则）与 IT 资产（外部信息）断裂 | LLM 判定无上下文，产生幻觉 |
| **风险识别依赖人工** | 个人资产（专家经验）与组织资产（风险规则）断裂 | 风险识别依赖专家，无法自动化 |
| **税务意见出具无法解释** | 组织资产（税务规则）与 IT 资产（财务数据）断裂 | 意见出具无数据支撑，无法追溯推理过程 |
| **规则更新影响未知** | 组织资产（规则）与 IT 资产（数据）断裂 | 修改规则后，无法分析影响范围，牵一发动全身 |

**传统方案的盲区**：
- 纯 LLM：无规则约束，产生幻觉
- 传统规则引擎：硬编码，无法热更新，影响分析困难
- Excel/PPT：无法自动化，无法追溯

## 竞品盲区：传统方案的资产断裂

| 方案 | 能力 | 盲区（资产断裂） | 对比 OntologyEngine |
|------|------|---------------------|---------------------|
| **传统规则引擎(Drools)** | 规则执行 | • 无图计算，无法关联 IT 资产<br/>• 无向量检索，无法语义检索<br/>• 个人知识无法沉淀为组织资产<br/>• 规则更新无影响分析 | OntologyEngine 支持图计算、向量检索、资产沉淀、影响分析 |
| **图数据库(Neo4j)** | 图存储与查询 | • 无规则引擎，无业务逻辑层<br/>• 个人知识无法结构化<br/>• 重度运维依赖，无法本地化 | OntologyEngine 内置规则引擎、四层推理、本地优先 |
| **向量数据库(Faiss)** | 语义检索 | • 无结构化推理，黑盒相似<br/>• 无法链接组织规则<br/>• 个人经验无法沉淀 | OntologyEngine 支持逻辑推理、规则链接、知识沉淀 |
| **LLM 微调** | 模型知识 | • 无法解释推理过程<br/>• 更新成本高，无法热更新<br/>• 组织规则无法实时更新 | OntologyEngine 规则可追溯、热更新、影响分析 |
| **RAG 检索增强** | 文档检索 | • 无多跳推理<br/>• 无规则执行，无法计算指标<br/>• 三层资产仍断裂 | OntologyEngine 支持图遍历、规则引擎、资产链接 |
| **GraphRAG** | 图+文档检索 | • 检索增强但无规则引擎<br/>• 个人知识仍无法沉淀<br/>• 无资产转换机制 | OntologyEngine 增加规则引擎、知识沉淀、资产转换 |
| **Agent Memory** | 对话记忆 | • 扁平存储，无结构化推理<br/>• 无组织知识沉淀<br/>• 无资产转换机制 | OntologyEngine 结构化推理、知识沉淀、资产转换 |

### 对齐 m-flow/KAG 的设计

| m-flow/KAG 概念 | 传统方案的盲区 | OntologyEngine 的补全 |
|------------------|----------------|---------------------|
| **m-flow 的 Cone Graph**（四层倒锥形图） | 传统 RAG 只有向量检索，无结构化推理 | OntologyEngine 对齐 Cone Graph，增加业务规则层 |
| **m-flow 的 Bundle Search**（图路由检索） | 传统图查询无语义加权，无法精准推理 | OntologyEngine 支持 Bundle Search，增加规则执行 |
| **KAG 的 Logical Form**（逻辑形式规划） | 传统方案无法将业务问题分解为可执行逻辑 | OntologyEngine 支持逻辑形式规划，L1→L4 推理链 |
| **KAG 的 Executor**（逻辑执行） | 传统方案无混合推理（图 + 向量 + 文本） | OntologyEngine 支持混合推理，三类资产融合 |

## 我们的解法：打通三类资产断裂

```
OntologyEngine = 图存储 + 规则引擎 + 向量检索 + 推理层
                 ─────────────────────────────────────────
                 + 三层资产链接（IT ↔ 个人 ↔ 组织）
                 ─────────────────────────────────────────
                 + 本地嵌入，声明式配置，可追溯决策
                 ─────────────────────────────────────────
                 + 作业过程即知识沉淀（个人 → 组织转换）
```

### 核心机制

| 断裂 | OntologyEngine 解法 | 关键机制 | 与 m-flow/KAG 的对齐 |
|------|---------------------|----------|---------------------|
| **IT ↔ 组织** | Schema 驱动：数据结构变更自动传播到规则 | • 域验证（ValueDomainValidator）<br/>• 影响分析（ImpactAnalyzer） | 对齐 KAG 的 OpenSPG 引擎（Schema 约束） |
| **个人 ↔ 组织** | YAML 声明式规则：专家经验直接编码为可执行逻辑 | • 个人归类规则（CategoryValueDomain）<br/>• 候选标记（candidate_for_organization）<br/>• 专家评审机制 | 对齐 m-flow 的 Procedural Memory（程序记忆） |
| **IT ↔ 个人** | 执行快照 + 条件拆解：系统告警有推理过程可审阅 | • ExecutionStepSnapshot（全链路追溯）<br/>• ConditionExplainer（中文解释） | 对齐 m-flow 的 Episode（场景存储） |
| **三层孤岛** | 统一本体模型 + 四层架构：所有资产用同一语言描述 | • KGML（统一知识描述语言）<br/>• L1→L2→L3→L4 推理链 | 对齐 m-flow 的 Cone Graph + KAG 的 Logical Form |

### 供应链金融风控：三层资产联动示例

```
┌────────────────────────────────────────────────────────────────┐
│ IT 资产:      发票流水 + 担保关系网络 + 实时交易数据                  │
│                 （数据表：invoices,担保关系, transactions）        │
├────────────────────────────────────────────────────────────────┤
│ 个人知识沉淀:   资深风控的"这个圈可疑"直觉 → 结构化为担保圈检测规则     │
│                 （user_123 的个人归类规则：担保圈 > 3 层，高风险）    │
├────────────────────────────────────────────────────────────────┤
│ 组织级资产:     合规准入政策 + 授信规则库 + 风险评级标准              │
│                 （v2.1 授信规则，FICO 风险评分）              │
└────────────────────────────────────────────────────────────────┘
                          ↓ OntologyEngine 融合推理
                          ↓
OntologyEngine 输出:
  • 准入判断（L2 归类）：应用个人归类规则 + 组织归类规则
  • 信用评分（L3 分析）：计算 FICO 分数，融合个人分析逻辑
  • 授信额度（L4 决策）：执行组织授信规则，生成决策
  • 利率定价（L4 决策）：根据风险等级，应用定价规则
  • 每个输出可追溯至具体资产层来源（ExecutionStepSnapshot）

传统方案: 3000 行 if/else（个人知识硬编码，三层断裂）
OntologyEngine: YAML 规则 + 三层链接 + DAG 执行（资产可追溯，热更新）
```

### Agent 知识增强：从检索到推理

```
用户问: "推荐几个靠谱的芯片供应商"

普通 RAG:  返回匹配文档片段（仅广度层，无推理）
            ↓
            结果：供应商 A、B、C（仅按关键词匹配，无风险判断）

GraphRAG:  返回关联实体和关系（深度层，但无业务规则）
            ↓
            结果：供应商 A（关联 3 个芯片类型，2 个项目）
                  但无法判断"靠谱"（无风险规则，无质量指标）

OntologyEngine:
  步骤 1：语义检索匹配供应商（广度层 / RAG）
          ↓
          从向量数据库检索：供应商 A、B、C、D、E

  步骤 2：图遍历发现供应链依赖（深度层 / 知识图谱）
          ↓
          从图数据库查询：A→芯片类型→项目→客户→风险等级

  步骤 3：规则引擎过滤资质 + 评估风险（推理层 / 三层资产链接）
          ↓
          L2 归类：应用个人归类规则（如"供应链深度 > 3 层，高风险"）
          L3 分析：计算指标（交付准时率 95%、退货率 2%、质量评分 88）
          L4 决策：执行组织规则（质量评分 > 80 且 风险等级 = 低，推荐）

  步骤 4：输出结果（可追溯决策）
          ↓
          结果：推荐供应商 B、C（质量评分高、风险低）
          依据：
            • 供应商 B：质量评分 92，风险等级低，交付准时率 98%
            • 供应商 C：质量评分 89，风险等级低，交付准时率 96%
            • 个人归类规则：user_456 偏好"供应链深度 ≤ 3 层"
            • 组织规则：v2.2 质量评分规则

传统方案：无
OntologyEngine：三层融合推理 + 可追溯决策 + 个人偏好适配
```
