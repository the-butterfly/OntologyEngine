# 为什么需要 OntologyEngine

## 痛点矩阵

| 痛点 | 现状 | 后果 |
|------|------|------|
| 规则散落在代码里 | 风控规则 = Python if/else | 改规则需发版，业务等不及 |
| 数据与知识割裂 | 数据在DB，知识在文档 | 模型用不全，决策拍脑袋 |
| AI 不懂业务 | LLM 通用知识 ≠ 行业规则 | 幻觉多，不敢用于核心决策 |
| 专家经验流失 | 老风控退休后规则成谜 | 组织能力退化 |

## 典型场景

**供应链金融风控**
```
输入: 供应商基本信息 + 发票流水 + 担保关系网络
输出: 准入判断 + 信用评分 + 授信额度 + 利率定价

传统方案: 3000行 if/else，改一行测一周
OntologyEngine: YAML规则 + 自动DAG执行，热更新
```

**Agent 知识增强**
```
用户问: "推荐几个靠谱的芯片供应商"

普通RAG: 返回匹配文档片段
OntologyEngine: 语义检索 + 资质过滤 + 风险评估 + 排名
```

## 竞品盲区

| 方案 | 盲区 |
|------|------|
| 传统规则引擎(Drools) | 无图计算，无向量检索 |
| 图数据库(Neo4j) | 无规则引擎，重度依赖 |
| 向量数据库 | 无语义推理，黑盒相似 |
| LLM 微调 | 无法解释，更新成本高 |

## 我们的解法

```
OntologyEngine = 图存储 + 规则引擎 + 向量检索 + 推理层
             ─────────────────────────────────────────
                      本地嵌入，声明式配置
```
