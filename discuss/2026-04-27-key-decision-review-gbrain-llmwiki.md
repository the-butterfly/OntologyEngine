## 一、三种知识管理范式的再审视

2026年4月，Agent记忆领域出现了两个标志性事件：Andrej Karpathy发布LLM-Wiki理念文件，Garry Tan（YC CEO）开源GBrain项目。它们与OntologyEngine当前采用的RAG范式形成了三足鼎立的架构哲学。

### 1.1 三种范式的核心差异

| 维度 | **RAG（OntologyEngine当前）** | **LLM-Wiki（Karpathy）** | **GBrain（Garry Tan）** |
|------|---------------------------|------------------------|------------------------|
| **核心隐喻** | 无状态Interpreter | 有状态Compiler | 持续运行的记忆OS |
| **重推理时机** | Query-time（每次查询从零检索） | Write-time（知识摄入时编译） | Write-time编译 + 后台维护 |
| **知识形态** | 原始文档碎片 | 结构化Markdown维基 | Compiled Truth + Timeline |
| **记忆增长方式** | 线性追加（ADD-only） | 复利增长（交叉引用+矛盾标记） | 复利增长 + 自动化维护 |
| **维护机制** | 无（或被动清理） | 手动触发Lint | 梦境循环（自动矛盾/过期/孤立检测） |
| **Token效率** | 基线（每次查询注入大量上下文） | **节省84.6-95%** | 中等（图查询节省） |
| **规模上限** | 百万文档级 | 百页级 | 万页级 |
| **人机分工** | 人类做Schema，LLM做检索 | 人类给原材料，LLM做编译 | 人类给方向，LLM做编译+维护 |

### 1.2 对OntologyEngine的核心启示

OntologyEngine当前本质上是一个**RAG+图增强**系统：原始文档分块存储（Layer-R），LLM提取实体关系存入图数据库（Layer-S），查询时并行检索+RRF融合。这属于典型的"Query-time重推理"模式。

**LLM-Wiki的启示**：如果Agent需要反复回答同一类问题（如"华为的风险等级是多少"），每次从原始文档重新检索并推理是极大的浪费。应该在知识摄入时就完成编译——生成结构化的摘要页、交叉引用、矛盾标记。

**GBrain的启示**：知识库不是静态的存储桶，而是需要**持续运行的维护循环**。就像操作系统需要垃圾回收和碎片整理，记忆系统需要自动检测矛盾、过期内容、孤立节点。

**OntologyEngine的机会**：当前设计已经具备"编译"的基础设施（ConsolidationPipeline将fragment→observation→entity→mental_model），但缺乏**编译产物的结构化存储**（LLM-Wiki的Markdown页）和**主动维护机制**（GBrain的梦境循环）。

## 二、关键决策点1：知识加工模式——编译 vs 检索

### 2.1 问题定义

当新的财报PDF进入系统时，Agent应该在**什么时候**完成知识加工？

| 模式 | 加工时机 | 查询时成本 | 存储成本 | 一致性保证 |
|------|---------|-----------|---------|-----------|
| **纯检索（Pure RAG）** | 查询时实时提取 | 高（每次查询都做一次提取） | 低（只存原文） | 无（每次提取结果可能不同） |
| **纯编译（Pure Wiki）** | 摄入时完整编译 | 极低（直接读编译产物） | 高（原文+编译产物） | 强（编译时已完成交叉引用和矛盾标记） |
| **混合模式（推荐）** | 摄入时编译摘要，查询时按需检索细节 | 中（摘要直接读，细节按需检索） | 中（原文+分层编译产物） | 中（摘要强一致，细节最终一致） |

### 2.2 OntologyEngine当前模式的审视

当前ConsolidationPipeline的设计：

```
fragment（原始摄入）
  → observation（LLM提取观察）
    → entity（LLM提取实体+关系）
      → mental_model（LLM归纳摘要）
```

**这是编译！但编译产物是扁平的。**

问题不在于"是否编译"，而在于：
1. **编译产物缺乏结构化交叉引用**：mental_model是一段文本，没有指向支撑它的observation/entity的显式链接（只有隐式的CONSOLIDATED_INTO边）
2. **编译是单向的**：fragment→observation→entity→mental_model，没有"mental_model发现矛盾后回写observation"的反向通道
3. **编译产物不可直接消费**：用户查询时，mental_model文本被作为搜索结果之一返回，而非作为"可直接回答的知识页"

### 2.3 LLM-Wiki的编译模式借鉴

LLM-Wiki的核心流程：

```
新源文档到达
  → LLM读取全文
    → 提取关键信息
      → 更新/创建实体页（如"华为"页）
        → 更新/创建主题页（如"供应链金融风险"页）
          → 标记与现有知识的矛盾
            → 更新交叉引用（index.md、相关页的反链）
              → 编译完成
```

**关键差异**：LLM-Wiki的编译产物是**结构化的Markdown页面**，包含：
- **实体页**：聚合所有关于某实体的信息，按时间线排列
- **主题页**：跨实体的综合摘要，包含引用链接
- **矛盾标记**：显式标注"此处与XX来源的说法不一致"
- **Index页**：自动维护的目录和导航

### 2.4 GBrain的Compiled Truth + Timeline双列结构

GBrain将每个知识条目存储为双列：

| Compiled Truth（编译真相） | Timeline（时间线） |
|--------------------------|-------------------|
| 当前最优摘要（如"华为2024年债务率65%，风险等级B"） | 按时间排列的所有版本和来源 |
| 自动更新的合成文本 | 不可变的原始记录序列 |

**设计意图**：
- **Compiled Truth**：面向查询的快速响应（直接读取，无需推理）
- **Timeline**：面向审计和更正的完整追溯（谁说了什么、何时说的、后来被什么取代）

### 2.5 对OntologyEngine的推荐改造

在不改变现有存储架构的前提下，引入**编译层（Compilation Layer）**：

```
┌─────────────────────────────────────────────────────────────┐
│                    查询路径（Query Path）                      │
│  User Query → 检查 Compiled Pages → 命中则直接返回            │
│           → 未命中则走传统检索（Layer-R + Layer-S）           │
├─────────────────────────────────────────────────────────────┤
│                    编译层（Compilation Layer）                │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │ Entity Page │  │ Topic Page  │  │ Contradiction Log   │  │
│  │ (per entity)│  │ (per theme) │  │ (cross-reference)   │  │
│  │ - 当前摘要   │  │ - 综合观点   │  │ - 矛盾标记          │  │
│  │ - 时间线    │  │ - 引用链接   │  │ - 待审核项          │  │
│  │ - 来源链接  │  │ - 相关实体   │  │ - 已解决项          │  │
│  └─────────────┘  └─────────────┘  └─────────────────────┘  │
├─────────────────────────────────────────────────────────────┤
│                    存储层（Storage Layer）                    │
│  Layer-R（原始碎片） + Layer-S（图结构） ← 现有架构不变        │
└─────────────────────────────────────────────────────────────┘
```

**编译触发条件**：

| 触发条件 | 编译动作 | 产物类型 |
|---------|---------|---------|
| 新entity被提取（proof_count ≥ 3） | 生成/更新Entity Page | 结构化摘要+时间线 |
| 同主题observation ≥ 5条 | 生成Topic Page | 综合观点+引用 |
| 新observation与现有entity属性矛盾 | 更新Contradiction Log | 矛盾标记+待审核提示 |
| 用户高频查询某entity（access_count > 10/周） | 预热Entity Page | 预编译摘要 |
| 周期性任务（每日/每周） | 全局Lint检查 | 孤立页标记、死链报告、过期提醒 |

**关键设计点**：编译层是**只读缓存+结构化索引**，不是替代存储层。Layer-R和Layer-S仍是唯一事实源，Compiled Pages是加速查询的派生产物。

## 三、关键决策点2：晋升机制——记忆如何从原始素材升级为知识资产

### 3.1 GBrain的晋升流设计

GBrain（以及其衍生项目WUPHF）引入了清晰的**晋升流（Promotion Flow）**：

```
Agent Notebook（个人笔记）
  → 当某条记忆看起来"持久"（重复出现的playbook、验证过的实体事实、确认的偏好）
    → Agent获得"晋升提示"
      → Agent决定将其提升到Wiki（团队共享）
        → 现在其他Agent可以查询它
          → Wiki记录"谁最后更新了这个知识点"，方便其他Agent @mention 询问详情
```

**核心原则**：
1. **自动提示，人工（或Agent）决策**：系统识别候选，但晋升需要主动确认
2. **Scope升级**：从个人（notebook）到团队（wiki）到组织（shared brain.db）
3. **溯源保留**：Wiki页始终指向原始记录者和最后更新者

### 3.2 OntologyEngine当前的"晋升路径"

当前设计中的晋升路径：

```
fragment（原始素材）
  → observation（LLM提取的观察） [自动，ConsolidationPipeline]
    → entity（LLM提取的实体+关系） [自动，Schema匹配]
      → mental_model（LLM归纳的摘要） [自动，proof_count ≥ 3]
        → procedure（经验抽象的技能） [半自动，episode ≥ 3 + 成功率统计]
```

**问题审视**：

| 问题 | 说明 | 风险 |
|------|------|------|
| 全自动晋升 | 从fragment到mental_model的晋升完全由LLM判断，无人工审核 | 错误信息被自动"固化"为高层的mental_model |
| 无Scope概念 | 所有记忆在同一个space内，没有个人/团队/组织的分层 | 个人观察与组织规则混存，权限和治理困难 |
| 晋升标准不透明 | proof_count ≥ 3、alignment_score > 0.7等标准是硬编码的 | 不同场景需要不同标准，缺乏可配置性 |
| 无降级机制 | 记忆只能"向上"晋升，不能"向下"降级或归档 | mental_model一旦生成永不消失，知识库膨胀 |

### 3.3 推荐的晋升机制设计

引入**五级资产等级 + 晋升/降级双通道**：

```
L0 原始素材（Raw Material）
  → 特征：未经处理的fragment/episode
  → 生命周期：7-30天TTL，被引用则延长
  → 晋升条件：被提取为observation或entity
  → 降级条件：无引用 + TTL到期 → 归档

L1 提取记忆（Extracted Memory）
  → 特征：observation/entity（Schema对齐后）
  → 生命周期：活跃期90天
  → 晋升条件：alignment_score > 0.8, proof_count ≥ 3, 人工review通过
  → 降级条件：alignment_score < 0.3 → 退回L0或删除

L2 摘要知识（Compiled Knowledge）
  → 特征：mental_model/opinion（经过交叉引用验证）
  → 生命周期：活跃期30天，需持续强化
  → 晋升条件：confidence > 0.8, access_count > 10/周, 无未解决矛盾
  → 降级条件：标记stale超过30天未刷新 → 退回L1

L3 程序资产（Procedural Asset）
  → 特征：procedure/rule_logic（经过成功率验证）
  → 生命周期：长期保留
  → 晋升条件：success_rate > 0.7, invocation_count ≥ 10, 人工审批
  → 降级条件：success_rate < 0.3 → 标记deprecated

L4 核心资产（Core Asset）
  → 特征：经人工确认的Schema定义、业务规则、合规要求
  → 生命周期：永久保留，版本管理
  → 晋升条件：人工审批 + 影响分析通过
  → 降级条件：版本替换（旧版本标记deprecated，不删除）
```

**晋升/降级的决策矩阵**：

| 触发事件 | 自动操作 | 人工审核 | 通知对象 |
|---------|---------|---------|---------|
| L0→L1（自动提取） | 是 | 否 | 仅日志 |
| L1→L2（摘要生成） | 是 | 可选（高价值entity） | 空间管理员 |
| L2→L3（程序提取） | 否（仅建议） | 必须 | 领域专家 |
| L3→L4（规则固化） | 否 | 必须 | 架构师+合规 |
| L2→L1（摘要降权） | 是（自动） | 否 | 仅日志 |
| L3→L2（程序废弃） | 是（自动标记） | 建议 | 空间管理员 |

## 四、关键决策点3：自动化维护——梦境循环 vs 被动级联更新

### 4.1 GBrain的"梦境循环"机制

GBrain最具创新性的设计是**梦境循环（Dream Cycle）**——一个后台自动化维护任务，模拟人类睡眠时的记忆整理过程：

```
梦境循环（每小时/每日触发）：
  
  Phase 1: 矛盾检测（Contradiction Detection）
    - 扫描所有Compiled Truth页
    - 对比Timeline中的不同版本
    - 标记逻辑不一致（如"债务率65%"vs"债务率45%"）
    - 生成Contradiction Report
  
  Phase 2: 过期检查（Freshness Audit）
    - 检查每个Compiled Truth的"最后验证时间"
    - 超过阈值（如30天未更新）的标记为"可能过期"
    - 检查底层来源是否还有效
  
  Phase 3: 孤立页清理（Orphan Detection）
    - 检查是否有Compiled Page无入链（从未被引用）
    - 检查是否有死链（指向不存在的Page）
    - 标记孤立页供人工review
  
  Phase 4: 自链接增强（Auto-Linking）
    - LLM分析新创建的Page内容
    - 建议与其他Page的链接关系
    - 自动添加双向引用
  
  Phase 5: 知识图谱补全（Graph Completion）
    - 检查知识图谱中的"缺口"
    - 如发现"华为"与"供应商B"有交易关系，但无"供应商B"的实体页
    - 生成"缺失知识提示"
```

**关键洞察**：GBrain的梦境循环是**主动的、全局的、周期性的**，而不仅仅是"新信息到达时触发级联更新"。

### 4.2 OntologyEngine当前的级联更新机制

当前设计中的级联更新：

```
新fragment到达
  → 触发Consolidation（提取entity/observation）
    → 影响评估（AnalyzeImpact遍历下游依赖）
      → 标记受影响的mental_model为stale
        → 后台队列刷新stale的mental_model
```

**对比分析**：

| 维度 | GBrain梦境循环 | OntologyEngine级联更新 |
|------|--------------|----------------------|
| **触发方式** | 主动（周期性后台任务） | 被动（事件驱动） |
| **扫描范围** | 全局（所有记忆） | 局部（仅受影响节点） |
| **检测能力** | 矛盾、过期、孤立、死链、图谱缺口 | 仅属性变更传播 |
| **处理深度** | LLM驱动的语义分析 | 基于图遍历的结构分析 |
| **资源消耗** | 可调度（低峰期运行） | 与写入流量绑定 |
| **实时性** | 最终一致（小时级） | 近实时（秒-分钟级） |

### 4.3 推荐的混合维护架构

**不是二选一，而是互补**：

```
┌─────────────────────────────────────────────────────────────┐
│                    维护架构（Maintenance Architecture）        │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  事件驱动层（Event-Driven）—— 近实时，秒-分钟级               │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 新信息到达 → 局部影响分析 → 标记stale → 入刷新队列      │   │
│  │ （现有CascadeUpdateEngine）                            │   │
│  └──────────────────────────────────────────────────────┘   │
│                            ↓                                 │
│  周期性后台层（Scheduled Background）—— 小时-天级             │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 梦境循环任务（DreamCycle）                             │   │
│  │   ├─ 全局矛盾扫描                                       │   │
│  │   ├─ 过期内容检测                                       │   │
│  │   ├─ 孤立节点/死链清理                                  │   │
│  │   ├─ 图谱完整性检查                                     │   │
│  │   └─ 知识质量评分（Knowledge Freshness Score）          │   │
│  └──────────────────────────────────────────────────────┘   │
│                            ↓                                 │
│  手动触发层（Manual Trigger）—— 按需                         │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 管理员审查仪表盘 → 处理梦境循环报告 → 确认/拒绝/修改    │   │
│  │ 紧急修复 → 直接操作底层存储                             │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**梦境循环的5个检查项映射到OntologyEngine**：

| 梦境循环Phase | OntologyEngine对应功能 | 现状 | 建议 |
|--------------|----------------------|------|------|
| 矛盾检测 | `ContradictionDetector` | 已设计，但未实现全局扫描 | 增加周期性全局扫描任务 |
| 过期检查 | `StalenessMonitor` | 已设计，但仅基于时间戳 | 增加语义过期检测（如"2024年报"在2025年Q2后可能过期） |
| 孤立节点 | 无 | 未设计 | 新增OrphanDetector：检查无入边的entity/mental_model |
| 死链 | 无 | 未设计 | 新增DeadLinkDetector：检查source_fragment_ids指向不存在的fragment |
| 图谱缺口 | 无 | 未设计 | 新增GraphGapDetector：利用Schema定义检查缺失的必需关系 |

## 五、关键决策点4：矛盾治理——人机信任边界与双轨制设计

### 5.1 LLM-Wiki的矛盾处理理念

Karpathy在LLM-Wiki中提出的核心原则：

> "LLMs don't get bored, don't forget to update a cross-reference, and can touch 15 files in one pass."

LLM-Wiki的矛盾处理流程：
1. **摄入时检测**：新源文档与现有wiki页对比，LLM自动标记不一致之处
2. **矛盾显式化**：在wiki页中直接标注"⚠️ 此处与[来源X]的说法不一致"
3. **人类决策**：用户看到矛盾标记后，决定"采纳新说法"、"保留旧说法"或"记录两种观点"
4. **LLM执行簿记**：一旦人类决策，LLM自动更新所有相关页的交叉引用

**关键特点**：
- 矛盾**不被隐藏**，而是**被显式展示**
- LLM**检测和标记**矛盾，但**不自动解决**
- 解决决策权始终在人类

### 5.2 GBrain的矛盾处理机制

GBrain的矛盾处理更工程化：

```
矛盾检测（自动化）
  → 生成矛盾报告（含冲突来源、置信度、影响范围）
    → 入ReviewQueue（按紧急度排序）
      → 管理员审查（人工决策）
        → 执行修正（LLM辅助更新所有下游引用）
          → 生成AuditLog（完整记录决策链）
```

GBrain的矛盾分类：
| 矛盾类型 | 自动处理 | 人工审核 | 示例 |
|---------|---------|---------|------|
| 数值更新（新版本替代旧版本） | 是 | 否 | 债务率从45%更新为65% |
| 事实反转（新证据否定旧结论） | 否（仅标记） | 必须 | "诉讼已撤诉"否定"华为涉诉" |
| 观点分歧（不同来源的不同解读） | 否 | 建议 | 分析师A看好评级，分析师B看跌 |
| Schema违反（数据不符合约束） | 是（拒绝写入） | 否 | 必填字段缺失 |

### 5.3 OntologyEngine矛盾治理的功能点审查

当前设计中的矛盾处理：

```python
# 当前设计的矛盾检测（from analyze_impact.py）
async def check_conflicts(entity_id, new_attribute_value):
    # 1. 检查同一实体同一属性是否有不同值
    existing = await get_entity_attribute(entity_id, attribute_name)
    if existing and existing.value != new_attribute_value:
        return ContradictionReport(
            type="attribute_mismatch",
            severity="high",
            requires_human_review=True  # 关键：总是要求人工审核
        )
```

**功能点评审**：

| 功能点 | 设计状态 | 问题 | LLM-Wiki视角 | GBrain视角 |
|--------|---------|------|------------|-----------|
| 矛盾检测 | 已实现（属性级比对） | 仅检测数值矛盾，无语义矛盾检测 | 应增加LLM语义矛盾检测 | 应增加置信度加权 |
| 矛盾展示 | 未设计 | 矛盾被隐藏在报告里，用户看不到 | **必须显式展示在知识页上** | 应生成结构化矛盾报告 |
| 矛盾解决 | 硬编码为"总是人工审核" | 无自动解决路径，所有矛盾都阻塞 | 符合"人类决策"原则 | 应区分自动/半自动/人工 |
| 矛盾传播 | 部分设计（AnalyzeImpact） | 新矛盾不会自动传播到依赖节点 | 应自动标记所有受影响页 | 应自动入ReviewQueue |
| 矛盾历史 | 无 | 无法追溯"某矛盾是如何解决的" | 应在页面上保留矛盾历史 | 应生成完整的AuditLog |

### 5.4 推荐的矛盾治理功能设计

**核心原则**：矛盾是知识演化的**正常信号**，不是**错误**。系统应该帮助人类**管理矛盾**，而不是试图**消除所有矛盾**。

**功能点1：矛盾可视化仪表盘**

## 六、关键决策点5：成本结构——Token效率的工程现实

### 6.1 LLM-Wiki声称的Token效率

据公开数据，LLM-Wiki相比纯RAG可节省 **84.6-95%** 的Token消耗。

**节省来源分析**：
1. **避免重复推理**：同一知识不需要每次查询都重新从原始文档提取和推理
2. **结构化摘要**：编译后的摘要页直接注入上下文，无需检索大量碎片
3. **交叉引用预建**：关系已经建立，查询时不需要LLM重新发现关联

### 6.2 OntologyEngine当前的Token成本结构

当前检索流程的Token消耗（估算）：

```
查询："华为2024年的风险等级是多少？"

Layer-R检索：
  - 检索top-5 fragments（约4000 tokens）
  - 注入Prompt（约500 tokens）
  - LLM提取和推理（约2000 tokens输出）
  → 总计：~6500 tokens

Layer-S检索：
  - 图遍历获取entity + relations（约1000 tokens）
  - RRF融合结果（约2000 tokens）
  - LLM生成回答（约1500 tokens输出）
  → 总计：~4500 tokens

并行执行（当前设计）：
  → 总消耗：~11000 tokens/次查询
```

**关键问题**：如果用户每天问10次"华为的风险等级"，每次都消耗11000 tokens，月消耗 = 3.3M tokens。

### 6.3 编译层的Token节省模型

引入编译层后的成本结构：

```
场景A：已编译的Entity Page存在
  查询："华为的风险等级？"
  → 直接读取Compiled Entity Page（~500 tokens）
  → LLM生成回答（~500 tokens）
  → 总计：~1000 tokens（节省91%）

场景B：需要展开证据链
  查询："华为的风险等级，请给出详细依据"
  → 读取Compiled Entity Page（~500 tokens）
  → EvidenceExpander按需展开observation+fragment（~3000 tokens）
  → LLM生成回答（~1500 tokens）
  → 总计：~5000 tokens（节省55%）

场景C：全新查询，无编译页
  查询："华为与供应商B的最近交易情况？"
  → 走传统检索路径（~11000 tokens）
  → 同时触发编译：生成"华为-供应商B交易"Topic Page（~5000 tokens，一次性）
  → 首次总计：~16000 tokens
  → 后续查询：~1000 tokens/次
```

**成本效益分析**（以月为单位，假设1000次查询）：

| 模式 | 编译投入 | 查询消耗 | 月总成本 | 单查询平均 |
|------|---------|---------|---------|-----------|
| 纯RAG（当前） | 0 | 11M tokens | $33 (按$3/M) | 11K tokens |
| 全编译（LLM-Wiki式） | 500K tokens（一次性） | 1M tokens | $4.5 | 1K tokens |
| **混合模式（推荐）** | 200K tokens（按需编译） | 3M tokens | **$9.6** | **3.2K tokens** |

**关键洞察**：编译不是免费的。初始编译需要消耗Token，但"热点知识"的查询成本可以下降90%。

### 6.4 GBrain的成本结构启示

GBrain的公开数据：

| 成本维度 | RAG（企业级） | LLM-Wiki | GBrain |
|---------|-------------|---------|--------|
| 初始部署 | $34,400-$58,000 | ~$500 | ~$1,000 |
| 月度运营 | $8,100-$19,500 | ~$50 | ~$25 |
| 检索延迟 | 50-200ms（轻载）/ 2s（重载） | 低（文件加载） | 2.4s（混合搜索） |
| 隐性成本 | 数据清洗（30-50%项目成本）、分块策略调优、重索引 | 持续知识工程、质量控制 | 自动化cron作业的计算成本 |

**对OntologyEngine的启示**：
1. **隐性成本是大头**：数据清洗、Schema调优、重索引占30-50%的项目成本，远高于LLM API费用
2. **编译降低了隐性成本**：因为知识在摄入时就被结构化，减少了后续的清洗和调优工作
3. **自动化维护的运营成本**：GBrain的梦境循环需要持续的计算资源，但这是可预测和可控的

## 七、关键决策点6：人机分工——谁负责原材料，谁负责簿记

### 7.1 LLM-Wiki的人机分工原则

Karpathy在LLM-Wiki中明确划分了人机边界：

> "You're in charge of sourcing, exploration, and asking the right questions. The LLM does all the grunt work — the summarizing, cross-referencing, filing, and bookkeeping that makes a knowledge base actually useful over time."

| 责任 | 人类 | LLM |
|------|------|-----|
| 原材料提供 | ✅ 提供源文档、数据、反馈 | ❌ |
| 探索方向 | ✅ 决定研究什么、问什么问题 | ❌ |
| 关键决策 | ✅ 矛盾解决、规则确认、优先级 | ❌ |

| 交叉引用 | ❌ | ✅ 建立链接、更新引用 |
| 簿记维护 | ❌ | ✅ 文件整理、目录更新、一致性 |
| 矛盾检测 | ❌（但审核结果） | ✅ 自动标记 |

### 7.2 GBrain的人机分工——更激进

GBrain进一步将LLM的自主权扩大：

| 责任 | 人类 | GBrain/LLM |
|------|------|-----------|

| 知识编译 | ❌ | ✅ 全自动 |
| 矛盾处理 | 可选（低级别自动） | ✅ 自动检测+自动解决（按规则） |
| 过期维护 | ❌ | ✅ 全自动（梦境循环） |
| 自链接增强 | ❌ | ✅ 全自动 |

### 7.3 OntologyEngine当前的人机分工审视

当前设计中的人机边界：

| 责任 | 人类（开发者/管理员） | LLM/系统 | 问题 |

**核心问题**：
1. **人类负担过重**：Schema定义、矛盾审核、实体对齐都依赖人类，不可扩展

## 八、案例审查：供应链金融风控Agent的30天事件流

### 8.1 场景回顾

某银行使用OntologyEngine构建供应链金融风控Agent，监控核心企业（华为）及其上下游供应商的信用风险。30天内发生以下事件：

```
Day 1:  导入华为2024年报 → 提取财务指标 → 信用评分=A
Day 5:  新闻：华为某子公司涉及诉讼 → Agent记录episode → 触发observation更新
Day 10: 用户询问："华为风险如何？" → Agent检索并回答
Day 15: 新导入征信报告：华为债务率上升 → 与Day 1的observation矛盾
Day 20: 用户更正："那起诉讼已经撤诉了" → 需要信息更正
Day 25: Agent自动归纳：近30天3次类似"债务率上升但随后澄清"模式 → 触发procedure提取
Day 30: 用户问："过去一个月华为风险判断为什么波动？" → 需要时序追溯和因果解释
```

### 8.2 逐日审查：每种范式的功能点表现

#### Day 1：年报导入

| 范式 | 处理流程 | 功能点评审 |
|------|---------|-----------|
| **OntologyEngine当前** | PDF→Layer-R fragments→Consolidation提取entity→EntityNode+MemoryUnitNode影子节点→L3 metric计算 | 编译发生，但产物是分散的节点和边，无结构化摘要页 |
| **LLM-Wiki** | PDF→LLM读取→生成/更新"华为"实体页→生成"2024年报摘要"主题页→更新index.md→标记与其他来源的矛盾 | **编译产物是可直接消费的页面**，包含时间线和交叉引用 |
| **GBrain** | PDF→提取结构化数据→更新Compiled Truth（华为债务率45%）→追加Timeline（来源：2024年报第32页）→运行自链接增强 | **双列结构**：Compiled Truth直接查询，Timeline支持审计 |

**关键发现**：OntologyEngine在Day 1已经完成了"编译"（提取entity、计算metric），但编译产物是**图数据库中的节点和边**，不是**人类可读的摘要页**。这导致Day 10查询时，系统需要重新从图中组装信息，而非直接读取预编译的摘要。

#### Day 5：新闻摄入

| 范式 | 处理流程 | 功能点评审 |
|------|---------|-----------|
| **OntologyEngine当前** | 新闻→Layer-R fragment→LLM提取observation("华为子公司涉及诉讼")→存入Layer-S | observation与华为entity无自动关联，需依赖标签匹配或人工打标 |
| **LLM-Wiki** | 新闻→LLM读取→更新"华为"实体页（新增"法律风险"段落）→标记与现有信息的关联→如果矛盾则标记 | **自动关联**：新信息被整合到已有实体页，而非孤立存储 |
| **GBrain** | 新闻→提取事件→更新Timeline（"Day5：子公司涉诉新闻"）→LLM评估对Compiled Truth的影响→如果置信度高则更新摘要 | **影响评估**：系统自动判断新信息是否应改变Compiled Truth |

**关键发现**：OntologyEngine的observation是**孤立节点**，与华为entity的关系依赖后续的图遍历。LLM-Wiki和GBrain都实现了**自动整合**——新信息直接进入相关实体页/时间线。

#### Day 10：用户查询"华为风险如何？"

| 范式 | 处理流程 | Token消耗 | 响应质量 |
|------|---------|-----------|---------|
| **OntologyEngine当前** | recall(query)→并行搜索mental_model/entity/observation/fragment→RRF融合→按权重排序→返回结果列表 | ~11K tokens | 返回碎片列表，Agent需自行组装回答 |
| **LLM-Wiki** | 读取"华为"实体页（已编译的摘要）→直接注入上下文→LLM生成回答 | ~1.5K tokens | **直接读取预编译摘要，响应快且一致** |
| **GBrain** | 读取Compiled Truth（华为当前摘要）→直接回答→如果用户要求"详细依据"→展开Timeline | ~0.5K tokens（快速回答）/ ~3K tokens（详细） | **分层响应**：快速回答读Compiled Truth，详细回答展开Timeline |

**关键发现**：这是三种范式**差距最大**的场景。OntologyEngine每次查询都重新检索和推理，而LLM-Wiki和GBrain直接读取预编译摘要。

#### Day 15：征信报告矛盾

| 范式 | 处理流程 | 矛盾处理 | 时效性 |
|------|---------|---------|--------|
| **OntologyEngine当前** | 新征信报告→提取entity(debt_ratio=0.65)→与旧值(0.45)比对→生成ContradictionReport→等待人工确认 | **阻塞式**：在人工确认前，查询返回哪个值？当前设计未明确 | 不确定（取决于人工响应速度） |
| **LLM-Wiki** | 新征信报告→LLM读取→与"华为"实体页对比→标记矛盾("⚠️ 债务率：新报告65% vs 年报45%")→**继续更新实体页**（添加新段落，保留旧段落） | **非阻塞**：矛盾被显式展示，但新信息仍然被记录 | 即时（无人工阻塞） |
| **GBrain** | 新征信报告→提取→与Compiled Truth对比→如果新来源置信度更高→**自动更新Compiled Truth**（65%）→追加Timeline（"Day15：征信报告更新"）→旧值保留在Timeline中 | **自动+可追溯**：新值取代旧值，但旧值永久保留在Timeline中 | 即时（自动处理） |

**关键发现**：OntologyEngine的**阻塞式矛盾处理**是企业场景的安全选择，但牺牲了时效性。GBrain的**自动更新+完整追溯**（Timeline）在保持时效的同时提供了审计能力。

**推荐改进**：引入GBrain式的**双列结构**和**自动解决规则**——数值更新类矛盾自动处理（新值supersede旧值），事实反转类矛盾标记待审核。

#### Day 20：用户更正

| 范式 | 处理流程 | 信息更正 | 级联影响 |
|------|---------|---------|---------|
| **OntologyEngine当前** | 用户输入→创建新observation("诉讼已撤诉")→与旧observation并存→无自动关联 | **无Supersedes机制**：旧observation仍然active | **无级联**：Day 5的episode和observation不受影响 |
| **LLM-Wiki** | 用户更正→LLM更新"华为"实体页→修改"法律风险"段落→添加"更新：诉讼已撤诉"→自动更新交叉引用 | **页面级更新**：更正直接反映在编译页中 | **手动级联**：LLM需要被指示更新其他相关页 |
| **GBrain** | 用户更正→创建新Timeline事件("Day20：用户告知诉讼已撤诉")→LLM评估对Compiled Truth的影响→更新摘要("曾涉诉但已撤诉")→**自动标记相关Timeline事件为superseded** | **自动级联**：Timeline中Day5的"涉诉"事件被自动链接到Day20的"撤诉"事件 | **自动传播**：Compiled Truth的更新自动反映到所有查询 |

**关键发现**：OntologyEngine在信息更正上最薄弱——ADD-only保留了历史，但**无Supersedes链**，**无级联更新**，旧信息仍然可能被检索到。

#### Day 25：模式归纳

| 范式 | 处理流程 | 程序提取 | 质量保障 |
|------|---------|---------|---------|
| **OntologyEngine当前** | 同主题episode≥3→触发ProcedureExtractionEngine→LLM抽象化步骤→生成procedure | **半自动**：触发条件是硬编码的，提取质量依赖LLM | **无验证**：procedure生成后不经过测试就可用 |
| **LLM-Wiki** | 无自动归纳机制（需人类指示"总结这3次经历"） | 无 | 无 |
| **GBrain** | 梦境循环检测到重复模式→生成"模式提示"→建议创建Skill（Markdown技能文件）→**人类确认后**创建 | **建议+确认**：系统提示，人类决策 | **有验证**：Skill创建后需经过测试 |

**关键发现**：OntologyEngine的procedure提取是**全自动**的（episode≥3即触发），这有**过度自动化**的风险。GBrain的**建议+确认**模式更安全。

**推荐改进**：procedure提取从"自动触发"改为"自动建议+人工确认"，并增加A/B测试机制（新procedure在小范围测试后再推广）。

#### Day 30：时序追溯查询

| 范式 | 处理流程 | 因果解释 | 证据链 |
|------|---------|---------|--------|
| **OntologyEngine当前** | recall(query)→并行搜索→RRF融合→返回mental_model+entity+observation+fragment列表→Agent自行组装 | **无因果链**：系统不提供"为什么波动"的因果结构 | **单层证据**：CONSOLIDATED_INTO链接observation→fragment，无multi-hop |
| **LLM-Wiki** | 读取"华为"实体页的时间线→LLM基于时间线生成因果叙述→交叉引用相关主题页 | **基于时间线**：时间线上的事件按顺序排列，LLM推断因果 | **页面级引用**：引用具体的wiki页和段落 |
| **GBrain** | 读取Timeline（按时间排序的所有事件）→LLM生成因果链→引用Compiled Truth的各版本变化→展示"从A到B到C"的演化路径 | **基于Timeline+Compiled Truth**：既有事件序列，又有状态变化 | **双列引用**：Compiled Truth展示状态，Timeline展示事件 |

**关键发现**：OntologyEngine在时序追溯上缺乏**叙事结构**（narrative structure）。LLM-Wiki和GBrain都通过**时间线**提供了天然的事件序列，便于LLM生成因果解释。

### 8.3 案例总结：三种范式的适用性矩阵

| 场景 | OntologyEngine | LLM-Wiki | GBrain | 推荐 |
|------|---------------|---------|--------|------|
| 快速事实查询（Day 10） | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 引入Compiled Page |
| 矛盾处理（Day 15） | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 引入双列结构+自动规则 |
| 信息更正（Day 20） | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 引入Supersedes+级联更新 |
| 时序追溯（Day 30） | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 引入Timeline视图 |
| 模式归纳（Day 25） | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ | 改为建议+确认模式 |
| 成本效率（Token） | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 混合模式 |

### 9.2 推荐的演进路径（融入LLM-Wiki + GBrain洞察）

```
Phase 1：编译层引入（1-2月）
├── 新增Compiled Page生成机制
│   ├── Entity Page（每entity一个，含当前摘要+时间线）
│   ├── Topic Page（每高频主题一个，含综合观点+引用）
│   └── 编译触发：新entityproof_count≥3 / 用户高频查询 / 周期性任务
├── 查询路径优化
│   ├── 优先检查Compiled Page（命中则直接返回）
│   └── 未命中则走传统Layer-R+Layer-S检索
└── 预期效果：热点查询Token消耗下降80%+

Phase 2：双列结构（2-3月）
├── 引入Compiled Truth + Timeline双列模型
│   ├── Compiled Truth：面向查询的当前最优摘要
│   └── Timeline：按时间排列的不可变事件序列
├── 矛盾自动处理规则引擎
│   ├── 数值更新：自动supersede（新值confidence > 旧值×1.5）
│   ├── 时序版本：自动标记valid_to
│   └── 事实反转：标记待审核（人工确认）
└── 预期效果：信息更正从"阻塞式"变为"自动+可追溯"

Phase 3：梦境循环（3-4月）
├── 周期性后台维护任务
│   ├── 全局矛盾扫描（每日）
│   ├── 过期内容检测（每日）
│   ├── 孤立节点/死链清理（每周）
│   └── 图谱完整性检查（每周）
├── 知识质量评分
│   └── Knowledge Freshness Score（每space一个，0-100）
└── 预期效果：知识库从"被动维护"变为"主动自愈"

Phase 4：晋升机制重构（4-5月）
├── 五级资产等级（L0-L4）
├── 晋升/降级双通道
│   ├── L0→L1：自动
│   ├── L1→L2：自动+可选审核
│   ├── L2→L3：建议+必须审核
│   └── L3→L4：建议+必须审核+影响分析
├── 降级规则
│   └── stale超30天 / confidence<0.2 / success_rate<0.3
└── 预期效果：记忆质量可控，知识库不无限膨胀

Phase 5：人机分工契约（5-6月）
├── 明确Human/AI/Shared责任边界
├── ReviewQueue仪表盘
│   ├── 矛盾审核队列
│   ├── Schema扩展建议队列
│   └── Procedure确认队列
└── 预期效果：人类负担降低70%，Agent自治能力提升
```

### 9.3 最关键的3个设计决策（更新版）

| 优先级 | 决策 | 推荐选择 | 参考范式 | 预期收益 |
|--------|------|---------|---------|---------|
| **P0** | 知识加工模式 | **混合编译：摄入时编译摘要页，查询时优先读取编译产物** | LLM-Wiki | Token效率提升80%+ |
| **P0** | 信息更正机制 | **双列结构（Compiled Truth + Timeline）+ 自动supersede规则** | GBrain | 更正时效从小时级降至秒级 |
| **P1** | 自动化维护 | **事件驱动级联（现有）+ 周期性梦境循环（新增）** | GBrain | 知识库从被动维护变为主动自愈 |

### 9.4 与三种范式的最终定位

OntologyEngine不应该成为LLM-Wiki或GBrain的复制品。它的独特定位是：

```
                    ┌─────────────────┐
                    │   OntologyEngine  │
                    │   （目标定位）      │
                    ├─────────────────┤
                    │  RAG的规模性      │ ← 支持百万级文档
                    │  +               │
                    │  Wiki的编译深度   │ ← 热点知识预编译
                    │  +               │
                    │  GBrain的自动维护 │ ← 梦境循环+晋升机制
                    │  +               │
                    │  Schema的治理力   │ ← L1-L4企业级约束
                    └─────────────────┘
```

**这不是简单的"取平均"，而是"分层融合"**：
- **大规模原始文档**：用RAG模式处理（Layer-R保留）
- **热点结构化知识**：用Wiki模式编译（新增Compilation Layer）
- **记忆自治维护**：用GBrain模式驱动（新增DreamCycle）
- **企业核心数据**：用Schema模式治理（保留L1-L4约束）
