## 一、案例定位

本案例用于补齐当前 `examples/` 中最大的空白：**用户如何直观看到 OntologyEngine 不是“只会找文档”的 RAG，也不是“只会吐结论”的规则引擎，而是能够把文档定义、结构化指标、规则阈值和消费结果连接起来。**

它面向的不是技术演示用户，而是更接近真实企业中的：

- 经营分析师
- 财务 BP
- BI 产品经理
- 经营分析 Agent 使用者

---

## 二、业务场景

场景设定为一家多区域运营的消费品零售集团，需要在 **月度经营复盘** 中回答以下高频问题：

- “华东大区 Q2 毛利率为什么低于预算？”
- “哪些门店毛利率不错，但回款速度明显偏慢？”
- “库存周转天数最高的品类是什么，是否需要做清仓动作？”
- “如果财务口径把毛利率从 `gross_sales` 改成 `net_revenue`，哪些结论会变化？”

## 四、为什么这个案例是“真实场景”

### 4.1 指标口径采用公开通行定义

本案例重点使用以下公开常见指标：

- **毛利率**：
  \[
  \frac{Revenue - COGS}{Revenue}
  \]
- **DSO**：
  \[
  \frac{Accounts\ Receivable}{Net\ Credit\ Sales} \times Days
  \]
- **DIO**：
  \[
  \frac{Average\ Inventory}{COGS} \times Days
  \]

### 4.2 数据采用“合成但真实”的经营结构

数据组织方式采用真实企业常见口径：

- 按 **区域 / 门店 / 品类 / 渠道** 切分
- 同时存在 **预算值、实际值、回款账龄、库存账龄**
- 文档层与结构化数据层并存：
  - 月报 PDF / Markdown 摘要
  - CSV/表格化经营数据
  - 指标字典
  - 规则阈值说明

## 五、案例闭环

本案例要求完整演示：

```text
经营文档 / 报表
  ↓
指标卡与规则包
  ↓
问数视图与异常清单
  ↓
问答结果 / 看板结果 / 报告结果
  ↓
回溯到指标版本、规则版本与原始证据
```

换句话说，用户不仅要能看到“答案”，还要能看到：

- 这个答案用了哪版指标公式
- 这个异常名单用了哪版规则阈值
- 这个结论来自哪些原始经营资料
- 如果改资产，答案和看板会如何变化
