# Case 2 场景说明 — 原始文档知识编译闭环

> **文件角色**: 业务场景与资产说明
> **对应愿景旅程**: J1 — 用户上传文档 → 完成知识编译（LLM-Wiki 模式）
> **对应核心问题**: P1 多源异构→统一可计算的知识表示

---

## 一、目标用户

- **知识管理员**：需要将企业制度、行业标准、合规文件编译为结构化知识
- **领域专家**：需要验证编译结果的准确性，确认矛盾标记
- **Agent 使用者**：需要消费编译后的结构化知识进行推理和查询

---

## 二、业务背景

某金融科技公司的合规部门收到一批新文档，需要纳入知识库：

| 文档 | 类型 | 来源 | 核心内容 |
|------|------|------|----------|
| `绿色融资指引_2026.pdf` | 监管文件 | 银保监会 | 绿色信贷分类标准、准入条件、风险权重 |
| `供应链金融操作手册_v3.2.md` | 内部制度 | 风控部 | 供应商准入流程、担保规则、审批权限 |
| `Q1经营分析报告.pptx` | 经营报告 | 财务部 | 各区域营收、毛利率、DSO、异常门店 |
| `风控会议纪要_2026Q1.md` | 会议记录 | 风控委员会 | 风险偏好调整、新增约束条件、专家判断 |

过去的问题是：
- 文档堆在共享盘里，Agent 只能做全文检索
- 同一事实在不同文档中有不同表达（如"毛利率"口径不一致）
- 文档更新后无法增量处理，只能重建索引
- 矛盾只能在查询时才发现，而非入库时标记

本案例要把"文档堆"变成"可编译、可查询、可执行、可治理的领域世界模型"。

---

## 三、本案例中的知识资产

### 3.1 输入资产（Raw Sources）

| 资产 | 类型 | 说明 |
|------|------|------|
| `docs/green_finance_guideline.pdf` | PDF 监管文件 | ~12 页，含表格和条款编号 |
| `docs/supply_chain_ops_manual.md` | Markdown 内部制度 | ~8000 字，含流程说明和权限矩阵 |
| `docs/q1_business_report.md` | Markdown 经营报告 | ~5000 字，含指标数据和区域分析 |
| `docs/risk_committee_minutes.md` | Markdown 会议纪要 | ~3000 字，含专家判断和约束条件 |

### 3.2 编译产物

| 产物 | 类型 | 说明 |
|------|------|------|
| Wiki 页面 | 知识页面 | 每个实体/概念自动生成独立页面 |
| 图谱节点 | EntityInstance | Schema 驱动的实体实例 |
| 关系边 | RelationInstance | 实体间的结构化关系 |
| 矛盾报告 | ContradictionReport | ingest 时检测到的冲突声明 |
| Living Overview | 总览页面 | 反映最新知识状态的自动摘要 |

### 3.3 消费资产

| 资产 | 用途 |
|------|------|
| 实体查询 | "绿色信贷的准入条件是什么？" |
| 规则执行 | "供应商 SUP_001 是否符合绿色融资标准？" |
| 矛盾检索 | "哪些文档对毛利率的定义不一致？" |
| 溯源查询 | "这条规则来自哪份文档的哪个段落？" |

---

## 四、本案例要解决的核心问题

### 4.1 多源文档 → 统一知识表示

- PDF 中的表格 → EntityInstance + 属性
- Markdown 中的流程 → Rule + 执行步骤
- 会议纪要中的判断 → Opinion + 置信度标签
- 经营报告中的指标 → MetricDeclaration + 数值

### 4.2 增量处理（Knowledge 编译一次）

- 首次 ingest：全量处理 4 份文档
- 更新 `supply_chain_ops_manual.md` 到 v3.3：仅处理变化部分（SHA256 缓存）
- 验证：未变化文档的图谱节点不受影响

### 4.3 矛盾检测前置

- `绿色融资指引` 定义"绿色企业"标准 A
- `风控会议纪要` 提出更严格的标准 B
- ingest 时立即标记矛盾，而非查询时才发现

### 4.4 溯源链路完整

- 每个 EntityInstance → `extracted_from` 原始文档 + 段落偏移
- 每条规则 → `defined_in` 制度文件版本
- 每个矛盾 → `supported_by` 冲突双方的原文引用

---

## 五、四类互索引关系在本案例中的落点

| 关系 | 在本案例中的含义 |
|------|------------------|
| `extracted_from` | 实体/规则从哪份文档的哪个段落提取 |
| `supported_by` | 哪个原文片段支撑当前判断 |
| `defined_in` | 当前规则/指标使用哪版制度定义 |
| `trace_to` | 编译结果如何流向消费视图和查询结果 |

## 六、案例闭环

```text
原始文档（PDF/MD/PPTX）
  ↓
SHA256 哈希比对 → 仅处理变化文件
  ↓
智能分块（QMD 断点评分 + AST 感知）
  ↓
Pass 1: 确定性提取（表格/标题/列表 → 结构化候选）
  ↓
Pass 2: LLM 语义提取（概念/关系/设计意图）
  ↓
矛盾检测（新文档 vs 已有知识）
  ↓
Wiki 页面 + 图谱节点写入
  ↓
Living Overview 自动更新
  ↓
消费：实体查询 / 规则执行 / 矛盾检索 / 溯源查询
```

---

## 七、这个案例为什么强

相比旧版"YAML 预定义 → 直接加载"的演示，本案例展示：

- **真实文档入口**：从 PDF/Markdown 开始，不是从 schema.yaml 开始
- **编译过程可见**：分块 → 提取 → 矛盾检测 → 写入，每步可验证
- **增量处理可测**：修改一份文档，验证其余不变
- **矛盾主动发现**：不是"查到了才知道矛盾"，而是"入库时就标记矛盾"
- **溯源链路完整**：每个结论都能回溯到原始文档的具体段落

这比单纯演示"知识图谱查询"更接近 OntologyEngine 的核心差异化能力。
